## 审查范围与方法

检查了 workspace 配置、MSRV、feature 边界、开发检查约定和固定规范来源。人工审阅重点是认证与刷新、HTTP/上传/下载重试和超时、SSE/流式结果处理、轮询、类型基础设施和结构化输出、Webhook 验证、RMCP 工具调用，以及 Codex JSONL 请求生命周期和 JWT 校验。资源 DTO 与端点覆盖主要结合已有单元测试、契约测试、编译隔离测试和 `xtask check` 验证。

这不是对所有源码逐行审阅的声明，也不代表证明项目不存在其他缺陷。API 语义按仓库固定的规范判断，并参考 [OpenAI 流式响应文档](https://developers.openai.com/api/docs/guides/streaming-responses)。本轮没有升级固定 API 规范或依赖版本。

## 已修复的问题

### 1. 获取外部令牌的回调卡住，会永久占用共享刷新状态

- 位置：`crates/openai-rs-client/src/workload_identity.rs`，`spawn_refresh`。
- 触发：启用 `workload-identity`，`SubjectTokenProvider` 返回的 future 长期处于 Pending。
- 原因：HTTP token exchange 配置了超时，但调用 provider 的过程在该超时之外。刷新又运行在独立任务中；外层请求即使被取消，共享的 `refreshing` 状态仍无法释放。
- 影响：使用同一认证实例的后续请求也会等待这个永远无法完成的刷新。
- 修复：为整个刷新过程设置超时，包括 provider、令牌交换和响应读取；超时也必须经过 `finish_refresh` 清理并唤醒等待者。
- 回归：`stalled_subject_provider_releases_the_refresh_slot` 验证首次 provider 卡住后能够结束，第二次 provider 调用可恢复认证。

### 2. 请求与握手的超时没有覆盖认证等待

- 位置：`auth.rs`、`transport.rs`、`multipart.rs`、`realtime.rs`、`responses_websocket.rs`、`beta_responses.rs`。
- 触发：认证缓存为空、令牌需要刷新，或从原客户端派生更短的 `with_request_timeout`。
- 原因：部分路径先计算剩余时间，再无限等待认证；另一些路径在认证结束后才启动整个请求的计时。
- 影响：实际总耗时超过配置的预算，甚至请求一直不返回；HTTP 请求还会使用认证之前的旧剩余时间。
- 修复：统一使用 `authorization_with_budget`，在剩余预算内等待认证，并在认证后重新计算剩余时间。覆盖 JSON、可重放上传、一次性上传、下载、音频等原始响应路径以及三类 WebSocket 握手；可重放 multipart 的表单重建也纳入预算。
- 回归：`request_budgets_bound_pending_authentication_in_every_http_lane` 覆盖五条 HTTP 路径，验证挂起认证在派生客户端的 30ms 预算内失败，并且没有发出 API 请求。

### 3. RMCP 请求入队阻塞时，取消和超时没有生效

- 位置：`crates/openai-rs-rmcp/src/executor.rs`，`call_cancellable`。
- 触发：rmcp 的有界 peer 请求队列已满。
- 原因：`send_cancellable_request(...).await` 位于取消/超时的 `select!` 外，原来的超时只约束取得请求 handle 后的响应阶段。
- 影响：已经配置 `ExecutionControl` 的工具调用仍可能在入队阶段一直等待。
- 修复：入队也同时等待取消和截止时间；响应阶段复用同一个计时 future，不重新获得完整预算。取得 handle 后的取消通知继续保持有界等待。
- 回归：`cancellation_interrupts_a_full_request_queue` 通过实际 rmcp 队列构造饱和状态，验证取消立即解除等待。测试关闭 Tokio 的协作式轮询预算，避免把调度让步误判为队列已满。

### 4. 连续 `$ref` 引用会静默丢失 schema 约束

- 位置：`crates/openai-rs-types/src/structured.rs`，`normalize`。
- 触发：字段带有 `$ref` 和 `description` 等同级属性，而引用的定义本身又是另一个 `$ref`。
- 原因：内联目标时无条件删除目标定义的 `$ref`。
- 影响：例如 `field → Alias → Actual` 中，`Actual` 的 `type`、`enum` 等约束消失，函数参数或结构化输出的 schema 被改变；纯别名组成的环也可能被意外截断。
- 修复：保留目标的下一层引用，让后续规范化继续解析，同时沿用循环检测和展开预算，保持字段自身描述的优先级。
- 回归：`sibling_ref_follows_aliases_without_losing_constraints`、`sibling_ref_rejects_an_alias_cycle`。

### 5. 把 `#/` 错误识别为文档根

- 位置：`structured.rs`，引用分类和 `resolve_ref`；历史决定 D0230。
- 原因：代码及旧测试认为 `#` 与 `#/` 都代表根。按照 [RFC 6901 第 6 节](https://www.rfc-editor.org/rfc/rfc6901#section-6)，`#` 才表示根，`#/` 选择根对象中名称为空字符串的属性。
- 影响：合法的空属性名引用被错误拒绝，错误类别也不准确；只有 `$ref` 的无效本地引用则可能直接通过。
- 修复：正确解析空属性名；缺失目标返回 `UnresolvableRef`；纯本地引用也先检查目标是否可解析。D0230 中增加了明确的更正记录。
- 回归：`slash_pointer_resolves_the_empty_property_name`、`missing_empty_property_reference_is_unresolvable_in_both_forms`，并保留原有根引用处理策略。

### 6. 轮询混用系统时钟和 Tokio 时钟

- 位置：`crates/openai-rs-client/src/poll.rs`，`poll_until`。
- 原因：截止时间使用 `std::time::Instant`，等待则使用 Tokio 定时器。
- 影响：Tokio 时钟被暂停或手动推进时，等待已推进，截止时间却没有相应推进。原有几项暂停时钟测试实际运行数分钟，并累计大量轮询记录。
- 修复：轮询统一使用 `tokio::time::Instant`。
- 回归：`polling_deadline_uses_the_runtime_clock` 验证 30ms 的轮询预算恰好在 30ms 模拟时间结束；原有服务端间隔提示与显式间隔测试继续覆盖节奏行为。

### 7. 丢弃 Codex 请求 future 后，资源和 JSONL 分帧状态未清理

- 位置：`crates/openai-rs-codex/src/app_server/client.rs`。
- 触发：调用方通过外层 `timeout`、`select!` 或任务取消，丢弃仍在等待写入或响应的请求。
- 原因：待处理表和 semaphore permit 的清理只存在于正常返回及 SDK 自身超时分支；`write_all` 被取消也没有统一的连接保护。
- 影响：无响应的请求会一直占据并发槽位；如果中断发生在部分 JSONL 帧已经写出之后，继续复用连接可能导致协议分帧错误。
- 修复：使用析构守卫清理 pending 条目。写入真正开始后若被取消，立即禁止复用连接并在后台完成关闭；等待写锁之前取消则只释放请求槽位。分离“已关闭”与“已开始清理”的状态，保证取消路径标记关闭后仍能执行清理。SDK 内部写入超时继续保留 `WriteTimeout` 分类。
- 回归：`dropped_request_releases_its_pending_slot` 通过实际请求 future 验证取消后容量恢复；`cancelled_write_blocks_reuse_and_completes_shutdown` 验证关闭守卫的即时阻止复用和异步清理。

### 8. Windows 上全功能 Clippy 检查被平台专属测试代码阻断

- 位置：Codex `runtime.rs` 和 `app_server/client.rs` 的测试模块。
- 原因：测试本身具有 Unix 或 macOS/arm64 条件，专用导入和 `fake_runtime` 辅助函数却没有同样的条件。
- 影响：Windows 编译产生 unused import/dead code 警告；项目要求的 `-D warnings` 将其视为错误。
- 修复：给专用导入和辅助函数补齐条件编译，保留跨平台测试。
- 验证：Windows、Rust 1.88.0 下全 workspace/all-targets/all-features Clippy。

### 9. Git 自动换行转换破坏固定规范和生成文件的字节一致性

- 位置：新增 `.gitattributes`；`spec/upstream` 与 `spec/contracts/*.json`。
- 触发：Windows checkout 配置 `core.autocrlf=true`。
- 证据：OpenAPI 文件原应为 3,405,126 字节，工作区却变成 3,490,490 字节，SHA-256 从 `5be8cde8…` 变成 `8404f0a3…`；`xtask check` 因此失败。
- 原因：仓库未约束这些需要精确字节验证的文件的换行处理。
- 修复：上游快照禁用文本转换；生成的 JSON 投影固定 LF。已从 Git 对象恢复现有快照和投影的原始字节，没有改动 schema 内容或放宽哈希检查。
- 验证：`xtask check` 已通过，包含两个上游规范来源和五个生成投影的一致性检查。

此外，`docs/development.md` 的 fuzz target 数量由“三个”修正为“四个”，补列实际存在的 `responses_input_item`。
